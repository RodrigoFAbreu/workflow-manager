# v2.3.1-002 — no documented edge from `IMPLEMENTING`/`SELF_REVIEWING_IMPLEMENTATION` back to plan revision/review

**Status:** documented **and** an authored-fix shipped as a second release
(distinct from `v2.3.1-001`'s "documented, not repaired"). Frozen v2.3.1
semantics are preserved; the fix ships as an additive `2.4.0` release built
from `2.3.1` plus a hand-authored overlay, never as an edit to
`distribution/workflow/2.3.1/`.
**Found:** during `plan-amendment-mechanism`'s own design work, prompted by
a real blocker in the sibling repository `workflow-controller`
(`workflow-controller-generation-1`, phase `SELF_REVIEWING_IMPLEMENTATION`,
checkpoint `CP9`) — read-only context, cited only for the blocker shape,
never touched from this work item.
**Affects:** `docs/ai-workflow/MILESTONE_WORKFLOW.md` (the state reference),
`scripts/workflow_state.py` (no writer exists for the edge).

## What it is

Frozen Workflow v2.3.1 has no documented transition out of `IMPLEMENTING` or
`SELF_REVIEWING_IMPLEMENTATION` back into plan revision/review.
`docs/ai-workflow/MILESTONE_WORKFLOW.md`'s state reference lists no such
edge, and `scripts/workflow_state.py` defines no writer that could produce
one: once a plan is approved and implementation begins, the only documented
paths forward are completing the milestone or applying review feedback
within the current plan's own checkpoint set. A work item whose approved
architecture turns out to need a genuine plan change mid-implementation —
not a review-feedback-shaped fix, but a change to the plan itself, its
registry, or its checkpoint set — has no legal path to make one. The only
escapes available are `USER_OVERRIDE`, an undocumented manual state edit, or
abandoning the work item and starting a new one, none of which this
Workflow sanctions as a substitute for a first-class transition.

`workflow-controller`'s real case: its approved `CP3`/`CP4` architecture has
no zero-work-item decision path, and its `REQ-T18` disposable-repository
scenario needs one. That is exactly the shape of change frozen v2.3.1 has no
documented lifecycle edge for.

## Why it is not repaired in place

Repairing it by editing `scripts/workflow_state.py`, `MILESTONE_WORKFLOW.md`,
or any other `distribution/workflow/2.3.1/` payload file in place would
violate this repository's own hard rule ("`distribution/` is generated, not
edited") and would break `tools/migrate.py --check`'s byte-identity
guarantee against the frozen upstream tag. `tools/migrate.py` itself cannot
produce this fix either way: it only extracts frozen upstream content
byte-for-byte, and the plan-amendment mechanism does not exist in
`repflow-android` at any tag — it originates here.

## How it is handled

Unlike `v2.3.1-001`, this defect gets a real fix, shipped as a **second,
authored** release rather than a repair to the frozen one:

- `migration/overlays/2.4.0/payload/` carries the new
  `AMENDING_PLAN` phase, its `/request-plan-amendment` command and writer,
  and the reconciliation mechanics that let an approved plan be revised
  mid-implementation without weakening any existing approval binding — the
  full design is recorded in this file's own sibling design document, in
  `migration/overlays/2.4.0/payload/docs/ai-workflow/WORKFLOW_V2_PLAN.md`'s
  new `### D-Plan-Amendment-1` through `### D-Plan-Amendment-8` sections.
- `tools/build_release.py` (new) builds `distribution/workflow/2.4.0/` from
  the frozen `2.3.1` base plus this overlay, verified and provenance-recorded
  (`overlay_delta` per replaced file), leaving `distribution/workflow/2.3.1/`
  byte-identical and untouched.
- `distribution/workflow/2.3.1/` and everything derived from it stays exactly
  as `tools/migrate.py --check` extracted it — this defect's disposition
  does not depend on, and does not wait for, any change to the frozen
  release.

## If a future upstream release repairs it

Should a future upstream `repflow-android` tag adopt an equivalent
plan-amendment mechanism natively, `tools/migrate.py` would extract it
directly and this overlay would become redundant for any target bootstrapped
from that later tag; existing `2.3.1`/`2.4.0` installations are unaffected
either way, per this repository's additive-only release discipline.

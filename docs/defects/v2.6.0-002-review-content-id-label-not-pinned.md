# v2.6.0-002 — the review-content-ID label in review feedback is not pinned

**Status:** **open — follow-up item for Workflow 2.7 (W1).** Worked around
operationally (every manual external verdict states the ID under both
labels); no Workflow or Controller code changed.
**Found:** `workflow-manager-trunk-model` (M1), `MANUAL_EXTERNAL_PLAN_REVIEW`
round 1, 2026-09-29. A Codex `REVISE` verdict stating only
`Reviewed review_content_id:` was refused by Workflow Controller `1.3.0` as
"inadmissible manual-stage feedback: review_content_id: feedback declares
None".
**Affects:** the `2.6.0` payload's review-feedback format, as written by
`.claude/commands/review-plan.md` and `.claude/commands/review-implementation.md`
and read by `scripts/workflow_fingerprint.py`'s
`parse_feedback_review_content_id`; and every consumer outside the Workflow
that parses the same line itself, today Workflow Controller `1.3.0`'s
`controller/evidence.py`. Every `"2.2"` work item whose manual external
verdict is written by hand or by an external model.

## What it is

`REVIEW_FEEDBACK.md` carries the reviewed `review_content_id` on a labelled
line, but no document fixes the label, and the Workflow itself uses two:

| where | label | role |
| --- | --- | --- |
| `.claude/commands/review-plan.md:113` | unspecified ("the recomputed plan-stage `review_content_id` as its own labelled line"); in practice `Reviewed review_content_id:` | writes |
| `.claude/commands/review-implementation.md:257` | `Reviewed review content ID:` | writes |
| `scripts/workflow_fingerprint.py` `_FEEDBACK_REVIEW_CONTENT_ID_RE` (used by `workflow_state.py:15811`, `/apply-plan-review`'s durable feedback check) | `review_content_id:`, optionally prefixed `Reviewed `; the spaced form does **not** match | reads |
| `REVIEW_PROTOCOL.md` "Required structure" | not listed (only the three binding fields) | — |
| Workflow Controller `1.3.0`, `controller/evidence.py:373` | exactly `Reviewed review content ID:`; the underscore form does **not** match | reads, at both manual external gates |

The two readers accept disjoint labels. A verdict stating only one of them
is refused by the other reader:

- **Only the underscore form:** the Controller refuses it at the manual gate
  (reproduced, above).
- **Only the spaced form:** `/apply-plan-review`'s durable check reads the ID
  as absent and refuses (`FeedbackNotForConsumedContentError`). That check
  runs only while the plan-review publication status is
  `PUBLISHED_UNBOUND` or `EDIT_IN_PROGRESS`
  (`PLAN_REVIEW_DURABLE_FEEDBACK_CHECK_STATUSES`, `workflow_state.py:15071`).
  It is skipped in the usual `BOUND` status, which is why spaced-only
  `REVISE` verdicts have worked in practice (the Controller repository's
  archived external plan reviews rev3, rev5 and rev6).

Nothing is corrupted by either failure: the verdict is refused before any
state write. The cost is a stalled automatic run that needs a human to
re-state the ID, and a reviewer template that looks correct but is only
correct in some publication states.

## Workaround in use

Every manual external verdict states the ID twice, same value:

```
Reviewed review_content_id: <hex>
Reviewed review content ID: <hex>
```

Each reader ignores the other's line, and `parse_feedback_review_content_id`
still sees exactly one distinct value. Verified against the `2.6.0` parser on
the M1 round-1 verdict.

## Required follow-up

In Workflow 2.7 (W1), through its own plan:

1. Pin one label in `REVIEW_PROTOCOL.md`'s "Required structure" and in both
   `/review-plan` and `/review-implementation`, and have
   `parse_feedback_review_content_id` accept the other form as a legacy
   alias, so existing verdicts and templates keep working.
2. Make feedback parsing Workflow-owned. The protocol's
   `record-external-result` operation (the long roadmap at de95195, section 1.9) is the
   natural home. The Controller then stops parsing verdict headers itself and
   cannot drift from the Workflow again.

A Controller-only interim fix (accept both labels in
`controller/evidence.py`) is small and removes the stall without waiting for
W1. That is the Controller lane's call, not this repository's.

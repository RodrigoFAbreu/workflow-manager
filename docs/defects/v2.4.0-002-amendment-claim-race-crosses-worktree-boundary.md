# v2.4.0-002 — the amendment-vs-checkpoint-claim race is closed only within one worktree root, not across the repository

**Status:** documented, not repaired in `2.4.0`. The guarantee this
release's own `migration/overlays/2.4.0/payload/docs/ai-workflow/
WORKFLOW_V2_PLAN.md` describes -- its `(2)→(8)` paragraph and the
narrowed `D-Plan-Amendment-1` precondition bullet it carries -- is real and
load-bearing *within one worktree root*; it is explicitly narrowed,
everywhere it is stated, to that scope rather than left as an unqualified
repository-wide claim. Cross-worktree amendment-versus-claim-start is out
of scope for `2.4.0`.
**Found:** `plan-amendment-mechanism`, round 9 external implementation
review (`XMODEL-R9-B1`), reproduced independently with real OS processes
against the shipped `distribution/workflow/2.4.0/payload/scripts/` before
this fix, and again against `migration/overlays/2.4.0/payload/scripts/`
after it (the code is unchanged by this fix; only the documented scope of
its own guarantee is corrected).
**Affects:** `workflow_state.claim_checkpoint`'s pre-publication phase
check and `workflow_state.request_plan_amendment`'s authoritative
`resolve_claim(...)` read/supersede-and-commit, for any work item whose
implementation is driven from more than one linked worktree of the same
repository.

## What it is

Round 8 (`XMODEL-R8-B1`) closed a real race: before it, a checkpoint claim
could be published, unguarded by anything in the `WORKFLOW_STATE.json`
domain, in the exact window between `request_plan_amendment`'s own
authoritative `resolve_claim(...)` read and that same call's later
`AMENDING_PLAN` commit. The fix was to run `claim_checkpoint`'s own
publication entirely inside `state_lock` -- the identical
`WORKFLOW_STATE.lock` `state_transaction` holds across
`request_plan_amendment`'s complete critical section -- so the two
operations are strictly ordered: whichever acquires the lock first
completes its entire critical section before the other's begins.

That fix rests on one premise the shipped design prose asserted
unconditionally: sharing the lock makes the two operations strictly
ordered, full stop. The premise is false whenever the two operations run
in **different linked worktrees of the same repository**, for two
independent reasons:

1. **The lock itself is not shared.** `STATE_LOCK_PATH` resolves as
   `repo_root / ".ai-review/runtime/WORKFLOW_STATE.lock"` -- one lock file
   *per worktree*. `claims_dir(repo_root)` (the checkpoint claim's own
   home) is `git_common_dir`-rooted and shared by every linked worktree.
   So worktree A's amendment and worktree B's claim publication take
   `flock` on two different inodes and are not serialized at all.
2. **Even perfectly serialized, the phase check cannot observe a foreign
   worktree's own commit.** `claim_checkpoint`'s phase check reads
   `repo_root / DEFAULT_STATE_PATH` -- *this worktree's own working-tree
   copy* of `WORKFLOW_STATE.json`. An amendment committed in worktree A
   writes A's own copy only; worktree B's own copy still says
   `IMPLEMENTING`, so B's phase check passes and publishes even when A's
   `AMENDING_PLAN` is already fully durable there, with no race at all.

Both were reproduced directly against the shipped `2.4.0` payload with two
real, separate OS processes, using `ScratchRepo.worktree(...)` (the same
fixture `TestRealProcessConcurrentTakeover` already uses for the
cross-worktree half of the checkpoint-claim mechanism):

```
lock A : /tmp/.../.ai-review/runtime/WORKFLOW_STATE.lock
lock B : /tmp/...-wt-b/.ai-review/runtime/WORKFLOW_STATE.lock
same lock file? False

amender (worktree A): success
claimer (worktree B): success, waited 0.0025s   <- never blocked
A phase              : AMENDING_PLAN
A plan_approval      : SUPERSEDED
live shared claim    : CP2 from .../wf-state-test-xb2_hse7-wt-b
```

and, for reason 2 alone, deterministically with no concurrency at all:

```
A phase: AMENDING_PLAN     B phase: IMPLEMENTING
claim_checkpoint(B) -> PUBLISHED CP2
claim visible from A: CP2  | A still AMENDING_PLAN
```

This is exactly the durable shape round 8's own required acceptance
criterion said must be impossible: `AMENDING_PLAN` persisted while a
checkpoint claim acquired during the same race remains outstanding, the
approval already superseded, reachable across worktrees even though it is
provably closed within one.

## Why it is in scope, not a hypothetical topology

The claim mechanism exists for nothing else. `request_plan_amendment`'s
own refusal message names the *foreign* worktree
(`"... worktree {outstanding_claim.get('worktree_root')!r}"`), and the
check it performs is `resolve_claim(...)`, not
`claim_is_this_worktree(...)` -- so the invariant is deliberately meant to
be cross-worktree. `_claim_or_refuse` raises
`CheckpointOwnedByOtherWorktreeError` ("resume it there");
`.claude/commands/milestone-implement.md` step 1c routes on "the worktree
that actually holds the claim" and step 1f reasons about "two worktrees
each" holding one; `.claude/commands/request-plan-amendment.md` carries no
worktree precondition of any kind. Two worktrees legitimately contending to
start a checkpoint versus amend the plan for the same work item is the
ordinary case this apparatus was built for -- this repository's own
`EnterWorktree`-driven sessions are exactly that shape.

## Why it is not repaired in `2.4.0`

Two structurally different fixes were on the table:

1. **A `claims_dir(repo_root)`-rooted lock** (the shape
   `guard_mutation_lock_path` already uses), acquired by both
   `claim_checkpoint` and `request_plan_amendment`'s own critical section.
   This closes reason 1 alone. It would also add a new primitive/edge to
   this module's own `item 372(h)` lock-order census and raw-edge
   derivation apparatus (`docs/ai-workflow/dry-run/
   verify_372h_lock_primitive_predicate.py`/
   `verify_372h_raw_edge_derivation.py`, mirrored into
   `migration/overlays/2.4.0/payload/docs/ai-workflow/dry-run/`), which
   would need a correspondingly declared new edge and a re-proved blocking
   sub-order -- a second, independent piece of concurrency-correctness
   engineering, not a one-line change.
2. **A repo-global witness** for `AMENDING_PLAN` the claim side can read
   regardless of which worktree it runs in -- necessary for reason 2, since
   no amount of locking makes a per-worktree working-tree file visible to
   another worktree's own phase check. `phase` today lives only in
   `WORKFLOW_STATE.json`, which is worktree-local, branch-scoped tracked
   content; a repo-global witness would be a new kind of object in this
   design (alongside the claim/guard/journal filesystem objects that
   already live under `claims_dir`), not an extension of an existing one.

Both are real, non-trivial additions to a concurrency-correctness
mechanism that has already gone through nine external review rounds to
reach its current, carefully-proved shape. Landing either under review
pressure, in the same round that found the gap, risks exactly the kind of
under-verified "fix" this workflow's own review discipline exists to
catch -- especially option 1, which would reopen the mechanically-checked
`item 372(h)` apparatus's own primitive census and edge table. The
external review that found this defect explicitly named narrowing the
documented scope, rather than half-fixing it, as one of three acceptable
closures (`XMODEL-R9-B1`'s "Required fix", option 3) -- correcting the
shipped prose that today asserts the broader property, and recording the
residual here, is what this repository has done instead.

**A third, cheaper option was raised and declined (`IMPL10-O1`, round
10).** A second `resolve_claim(...)` re-check immediately before
`request_plan_amendment`'s own supersede, in place of the single
authoritative read it performs today, would narrow reason 1's exposure
window from the full registry-load/`git rev-parse`/history-walk interval
down to microseconds, at no new primitive and no `item 372(h)` edge. It is
declined for `2.4.0`, for the same reason options 1 and 2 above are: it is
a real change to the mechanism's own critical section under review
pressure, in the same round the residual was found, and it would still be
narrowing rather than closure -- reason 2 (the stale foreign phase read)
is untouched either way, so the residual this file records would remain,
only smaller. Left for a future release to take up alongside the two
closures above, not attempted here.

## How it is handled

- `migration/overlays/2.4.0/payload/scripts/workflow_state.py`'s
  `claim_checkpoint` docstring, `migration/overlays/2.4.0/payload/docs/
  ai-workflow/WORKFLOW_V2_PLAN.md`'s `(2)→(8)` paragraph and its
  `D-Plan-Amendment-1` precondition bullet, and `migration/overlays/2.4.0/
  payload/.claude/commands/request-plan-amendment.md` step 1 all now state
  the guarantee as scoped to one worktree root, name both independent
  reasons it does not extend further, and point here.
- Round 10 closed three further sites the same review round found still
  unqualified (`IMPL10-R1`): the `(2)→(8)` row's own bracket annotation
  inside `WORKFLOW_V2_PLAN.md`'s eleven-edge table (as distinct from the
  narrowing paragraph ~250 lines later, which was already correct); the
  `IllegalCheckpointStartPhaseError` class docstring's second paragraph
  (`workflow_state.py`); and that same error's runtime refusal message
  raised by `claim_checkpoint`, the text an operator actually sees at
  refusal time. All three now name the one-worktree scope and point here.
- Round 11 closed a fourth site the same review round found still
  unqualified (`IMPL11-R1`):
  `docs/ai-workflow/dry-run/verify_372h_raw_edge_derivation.py`'s own
  module docstring (overlay and distribution copies, byte-identical), a
  parallel copy of the same sentence the `(2)→(8)` row already carried,
  which round 10's sweep missed because it lives in a different file. Now
  narrowed to one worktree root and points here, matching every other
  site.
- `migration/overlays/2.4.0/payload/scripts/workflow_state_test.py` gains
  permanent regression tests pinning this exact, documented boundary --
  both the deterministic case (a durable `AMENDING_PLAN` in one worktree is
  invisible to another worktree's own `claim_checkpoint` phase check) and
  the racing case (two real processes, one per worktree, both succeed,
  reproducing the evidence above) -- so a future change that silently
  narrows this behavior is caught. Widening coverage is only partial
  (`IMPL10-O3`): both tests would still pass if a fix closed reason 1 alone
  (a `claims_dir`-rooted lock) while reason 2 remained open, since the
  claimer's phase check would still be blind and both sides would still
  succeed -- the claimer would merely block first before doing so. Neither
  test alone proves reason 2 is closed; only a fix that closes both would
  be caught failing to widen.
- The within-one-worktree guarantee itself is unchanged and remains
  covered by round 8's own `TestAmendmentClaimRaceRealProcesses`, now
  joined by the claimer-wins-the-lock ordering (round 8's own acceptance
  criterion 6, completed this round) and a direct pin that
  `transition_checkpoint_in_progress`'s own phase guard is not made
  redundant by `claim_checkpoint`'s (both real, both necessary, for
  different sets of call sites).

An operator driving one work item's implementation from more than one
linked worktree at once should treat this precondition as advisory, not
authoritative, across worktrees: finish or release a checkpoint claim from
whichever worktree holds it before requesting an amendment from another.

## If a future release repairs it

A future release that wants to close this residual needs both fixes above,
together, plus a corresponding widening of the `item 372(h)` primitive
census and raw-edge table, and new cross-worktree regressions proving the
combined result actually removes both reasons 1 and 2 -- not the first
alone, which would remove reason 1 while reason 2 continued to let a
foreign worktree's stale phase read through, or the second alone, which
would still race unserialized. Until then, this file is the record that
the gap is known, understood, and deliberately left open, not
undiscovered.

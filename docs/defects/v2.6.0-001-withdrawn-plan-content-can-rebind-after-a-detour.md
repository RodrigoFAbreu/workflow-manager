# v2.6.0-001 — withdrawn plan-stage content can re-bind after a detour

**Status:** **open — mandatory follow-up correctness item.** Partially
mitigated in `2.6.0` (the stale-approval shortcut is closed, see
"`2.6.0` disposition"). The stronger "never re-binds" semantics the
approved plan states are **not** enforced by `2.6.0`, and must be decided
and implemented by a later Workflow release through its own plan.
**Found:** `workflow-review-artifact-and-concurrency-hardening`
implementation self-review (minor finding 5), then
`LOCAL_MODEL_IMPLEMENTATION_REVIEW` round 1, Important 1 (reproduced).
**Affects:** the `2.6.0` overlay's `scripts/workflow_state.py`:
`_assert_not_consumed`, `_write_consumed_plan_review_binding`,
`withdraw_plan_review`, `publish_plan_revision` and
`bind_plan_review_bundle`. Every `TWO_STAGE_PLAN_REVIEW_VERSIONS`
(`"2.1"`/`"2.2"`) work item in a repository running `2.6.0`.

## What it is

`plan_review_binding.consumed` is a **single slot** holding the content
most recently taken out of review. Every `CONSUMED` writer overwrites it
from its own inputs. That is the record shape plan revision 8 pins in
section 5.3 item 2: `{review_content_id, plan_revision, legacy}`, written
"never from a prior record".

Neither `withdraw_plan_review` nor a `REVISE` discards `plan_review_stages`
(section 5.3 item 7). This sequence re-binds content that was already
reviewed:

1. Content A is dual-approved, and the item is at `AWAITING_PLAN_APPROVAL`.
2. `/milestone-plan <id>` withdraws it (`consumed` = A).
3. Content B is published and bound, then withdrawn again (`consumed` = B).
4. A's bytes are restored. `publish_plan_revision` and
   `bind_plan_review_bundle` both accept A, and the item is at
   `AWAITING_LOCAL_PLAN_REVIEW`, `BOUND` to A.

This falsifies section 5.3's closing guarantee ("In no row can
already-reviewed … content enter review") and its recovery-table row
("the withdrawn content is `CONSUMED` and cannot re-bind"). The same is
true of the prose that mirrors them: `milestone-plan.md` (withdrawal
report), `MILESTONE_WORKFLOW.md`, `review-plan.md`,
`request-plan-amendment.md` and `WORKFLOW_V2_1_OPERATOR_REFERENCE.md`
("`CONSUMED` and never binds again without an edit"; added at
implementation review round 2, O4).

## Why it was worse before the mitigation

At step 4 the content-keyed ledger still reads A's two `APPROVE`s, so
`plan_approval_gate_reachable(...)` returns `True` at
`AWAITING_LOCAL_PLAN_REVIEW`. Through reviewed commit `87ecfe8`, neither
`apply_plan_approval` nor `/approve-review plan` required
`AWAITING_PLAN_APPROVAL`. So approval was reachable from a phase that
should never reach it. This was never approval of *unreviewed* content: A
really was dual-approved, and the user still had to invoke approval.

## `2.6.0` disposition (partial)

- **Closed: the stale-approval shortcut.** `apply_plan_approval` refuses a
  `TWO_STAGE_PLAN_REVIEW_VERSIONS` item at any phase other than
  `AWAITING_PLAN_APPROVAL` (`PlanApprovalPhaseError`, commit `799b80d`),
  and `approve-review.md` step 0 states the gate. Only the manual stage's
  own `APPROVE` writes that phase, so a re-bound A must be reviewed afresh
  by both stages before it can be approved.
  `TestPlanApprovalPhaseGate` pins the full sequence above.
- **Not closed: the re-bind itself.** A still re-binds and re-enters review
  as an ordinary round. Fully enforcing "never re-binds" needs a
  design/schema change: a consumed-content history, or a different
  `CONSUMED` model. Either one contradicts plan revision 8's pinned record
  shape. So it cannot be introduced during that work item's
  `APPLYING_REVIEW_FEEDBACK` round, where `/request-plan-amendment` is
  unavailable (`_AMENDMENT_REQUEST_ALLOWED_PHASES` is
  `{IMPLEMENTING, SELF_REVIEWING_IMPLEMENTATION}`). The user directed that
  no consumed-history schema be invented in that remediation round.

## Required follow-up

A later Workflow release's plan must decide, and then implement and test,
one of:

1. **Enforce the stronger semantics.** Keep a durable record of every
   consumed `review_content_id` (or an equivalent model), so that
   publishing or binding any content ever taken out of review refuses. The
   plan must define the record shape, the migration of `2.6.0`
   single-slot records, and the downgrade posture.
2. **Narrow the guarantee.** State normatively that only the most recently
   consumed content is refused, that earlier-consumed content may return
   for a *fresh* two-stage review, and that approval is gated on
   `AWAITING_PLAN_APPROVAL`. Update section 5.3's normative text and every
   command document that mirrors it.

Whichever is chosen, the regression test is the withdraw → detour →
restore sequence above, asserting the chosen outcome.

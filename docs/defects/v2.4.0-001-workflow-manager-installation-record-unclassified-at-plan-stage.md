# v2.4.0-001 — a pre-existing work item's plan-stage classification does not know about `.workflow-manager/installation.json`

**Status:** repaired going forward (`generate_artifacts_declarations`'s
plan-stage `excluded_prefixes` now includes `.workflow-manager/`), not
repaired retroactively for a work item whose own declarations file was
already generated before this fix. `2.5.0` widens the same forward-only
repair to the **implementation** stage (`implementation-review-two-stage`
CP9) -- see "`2.5.0` disposition" below. **Closed in `2.6.0`** for the
legacy items too, without editing any declarations file -- see "`2.6.0`
disposition" below.
**Found:** `plan-amendment-mechanism` CP8, disposable-repository update-path
validation (`docs/ai-workflow/PLAN_AMENDMENT_MECHANISM_PLAN.md` section 4,
scenario 2: `IMPLEMENTING`, bootstrap `2.3.1`, drive a synthetic work item
partway through checkpoints, `update` to `2.4.0`).
**Affects:** `<work_item_id>-artifacts.json`'s `plan_stage.excluded_prefixes`
for any work item generated before this fix landed; consumed by
`workflow_fingerprint.compute_review_content_id_plan_stage_at_commit`
(`assert_all_changed_paths_classified_commit`), reached from
`workflow_state.implementing_entry_reachable` -> `approval_is_current` ->
`approval_review_content_id`.

## What it is

`workflow_manager.install.bootstrap`/`update` write a durable record of
what release is installed to `.workflow-manager/installation.json`, and the
record is meant to be committed (`installation.py`'s own module docstring:
"the one thing a target cannot afford to lose"). That path is
`workflow_manager`'s own tooling invention -- it is never part of any
Workflow release's distributed payload/templates, and it never existed in
the real upstream `repflow-android` repository this Workflow was migrated
from. Neither `workflow_fingerprint.PLAN_STAGE_EXCLUDED_PREFIXES` (the
frozen, upstream-inherited constant) nor, until this fix,
`workflow_state.generate_artifacts_declarations`'s own generated defaults
name it anywhere.

Every work item's own plan-stage `review_content_id` is recomputed against
every path changed between its `base_commit` and the commit under test
(`assert_all_changed_paths_classified_commit`), and any path not resolved
to *protected* or *excluded* raises `UnclassifiedPathError` -- fail-closed,
by design, for a genuinely novel path. `.workflow-manager/installation.json`
changes on every `update()` (the recorded `workflow_version`, managed-file
digests, etc.). A repository that commits that update -- the ordinary,
expected way to make an `update()` durable -- therefore introduces exactly
one such novel, changed path into the interval of *every* work item whose
`base_commit` predates the update.

The consequence is not a clean refusal: `UnclassifiedPathError` propagates
as an uncaught exception through `approval_review_content_id` ->
`approval_is_current` -> `implementing_entry_reachable`, which
`/milestone-implement`'s own step 1a (both governing-version branches) and
`/request-plan-amendment`'s own widened precondition both call before doing
anything else. A pre-existing `IMPLEMENTING`/`SELF_REVIEWING_IMPLEMENTATION`
work item whose repository was updated across a committed
`.workflow-manager/installation.json` change cannot resume implementation
*or* request a plan amendment -- both entry points crash instead of
reporting a clean, actionable refusal.

## Why it happened here

`generate_artifacts_declarations`'s inherited defaults
(`fingerprint.PLAN_STAGE_EXCLUDED_PREFIXES`, migrated byte-for-byte from
`workflow-v2-1-core`'s own real plan) are real `repflow-android` paths
(`app/`, `gradle/`, `docs/adr/`, ...) -- correct for that repository, and
silent on anything `workflow_manager`'s own bootstrap/update tooling
writes, since that tooling did not exist in that context. This repository
is the first to combine "a live Workflow-governed work item" with "a
repository actually managed by `workflow_manager`'s own `update()`," which
is precisely what CP7/CP8's disposable-repository fixtures exist to
rehearse before any real managed repository (e.g.
`~/Workspace/workflow-controller`) attempts the same update.

## Why it is not repaired retroactively

`generate_artifacts_declarations` is a plan-time generator: its output is
committed into `<work_item_id>-artifacts.json`, which is itself a
plan-stage protected path. Widening the *live* function's defaults (this
fix) changes nothing for a work item whose declarations file already
exists -- exactly the "widen the template, not the frozen constant" rule
salvage audit I7/I8 already established for the same generator, applied
consistently here. Editing an *existing* work item's own
`<work_item_id>-artifacts.json` after the fact to add this exclusion would
itself change plan-stage-protected content out from under a standing
`plan_approval`, staling it (or worse, silently not staling it, which is
the actual defect class `AmendmentReconciliationInputsMissingError` and
friends exist to prevent elsewhere in this same mechanism) -- exactly the
kind of unilateral, unapproved repair this repository's own workflow
guards against.

## How it is handled

Going forward, any work item whose plan/registry/mapping is generated
under this fix (`generate_artifacts_declarations` in
`migration/overlays/2.4.0/payload/scripts/workflow_state.py`, and hence
in `distribution/workflow/2.4.0/` once rebuilt) is unaffected: `update()`
committing `.workflow-manager/installation.json` never lands as an
unclassified path in its own plan-stage interval.

A work item whose declarations file predates this fix (any item created
under `2.3.1`, or under an earlier, unfixed `2.4.0` build) remains exposed:
if its repository ever commits an `update()`-driven change to
`.workflow-manager/installation.json` inside that item's own
`base_commit..HEAD` interval, `implementing_entry_reachable`/
`/request-plan-amendment` will raise `UnclassifiedPathError` rather than
proceeding. The operator-facing mitigations, in order of preference:

1. **Do not commit `.workflow-manager/installation.json`** in a repository
   with a live work item mid-update (add it to a local, uncommitted
   exclude, e.g. `.git/info/exclude` -- it is read from the working tree
   only, never from Git history, so nothing about `workflow_manager`'s own
   behavior requires it to be tracked). This sidesteps the interval
   entirely and is what this fix's own CP8 test suite does.
2. If it was already committed inside a live item's interval, a maintainer
   with plan-approval authority can widen that one item's own
   `<work_item_id>-artifacts.json` `plan_stage.excluded_prefixes` by hand,
   the same way `/milestone-plan` would author it fresh -- an explicit,
   reviewed edit, not an automatic repair, since it changes plan-stage-
   protected content.

## If a future release repairs it further

The portable form is a `workflow_fingerprint.PLAN_STAGE_EXCLUDED_PREFIXES`
entry for `.workflow-manager/` in a future frozen release -- but that
constant is upstream-inherited and this repository does not author
upstream `repflow-android` releases, so this is recorded here for whoever
next extracts a Workflow release that this tooling also bootstraps.

## `2.5.0` disposition (`implementation-review-two-stage`, §8, CP13)

**Implementation-stage symmetry widened (CP9); still not retroactively
repaired.** `2.4.0`'s own fix widened only
`generate_artifacts_declarations`'s **plan-stage** default
`excluded_prefixes`. Its **implementation-stage** default template kept the
identical gap: a freshly generated declarations file's implementation-stage
half said nothing about `.workflow-manager/installation.json`, so an
`update()`-driven commit to that record landing inside a live item's own
implementation-stage interval still raised `UnclassifiedPathError`, exactly
as the plan-stage gap once did. `implementation-review-two-stage` was
itself a fresh victim of precisely that — it had to hand-fix its own
`implementation_stage` declarations before it could generate an
implementation bundle at all.

CP9 widens the implementation-stage default the same way, in
`migration/overlays/2.5.0/payload/scripts/workflow_state.py`:
`implementation_stage.excluded_prefixes` now carries `.workflow-manager/`
alongside the plan-stage entry `2.4.0` added, with the same justification
text and the same forward-only rule. The overlay's own
`scripts/workflow_state_test.py` pins it, in
`GeneratedDeclarationsWorkflowManagerImplementationStageWideningTest`
(three tests: the implementation-stage default classifies
`.workflow-manager/installation.json` `excluded` for both work-item types,
and the widened prefix is symmetric with the plan-stage default).

**Forward-only, deliberately.** No existing work item's own
already-generated declarations file is edited — editing one after the fact
would itself stale a standing approval, which is the same reasoning this
record already gives above for the plan-stage case, and the reason that
case was not retroactively repaired either. So "Why it is not repaired
retroactively" and the operator mitigations above still apply verbatim to
every work item that already exists, at both stages. What changes is only
that a *future* work item's first-ever implementation-stage declarations
file is generated already-correct — the same guarantee `2.4.0` gave the
plan stage, now given to both.

## `2.6.0` disposition (`workflow-review-artifact-and-concurrency-hardening`, CP1, CP7)

**Closed.** `2.6.0` repairs the legacy-item half this record left open,
still without editing any existing `<id>-artifacts.json`
(`D-Tooling-Ambient-Classification`, the plan's section 5.2).
`migration/overlays/2.6.0/payload/scripts/workflow_fingerprint.py` adds
`TOOLING_AMBIENT_EXCLUDED_PATHS = frozenset({".workflow-manager/installation.json"})`,
an exact-path, release-derived terminal fallback. `classify_path` and
`classify_path_implementation_stage` consult it only after every declared
classification has failed, immediately before the `UnclassifiedPathError`
raise. A declaration still decides first, and the constant never enters a
hashed classification set. So every digest `2.5.1` could compute is
byte-identical under `2.6.0`, and a digest that used to raise because a
committed `workflow_manager update` rewrote the installation record now
returns. For a plan-approved item that value equals the stored
`plan_approval`, so `implementing_entry_reachable` holds again.

Pinned by:

- `workflow_fingerprint_test.py`'s `TestToolingAmbientExcludedPaths`
  (8 tests): the fallback at both stages, declaration precedence, and
  digest invariance;
- `workflow_state_test.py`'s
  `TestImplementingEntryReachableAfterInstallationRecordUpdate` and
  `TestImplementingEntryReachableSecondItem`: entry reachability across a
  committed installation-record rewrite.

The operator mitigations above remain valid, but are no longer needed.

**A separate hazard, out of scope and not repaired** (the plan's sections
2 and 3.2). Reproducing this defect showed a second, independent effect of
`workflow_manager update` on a `process` work item. The update rewrote 21
*protected* `scripts/`/`.claude/commands/` paths (a `process` item's own
implementation surface) in the middle of that item's implementation. That
moves the item's implementation-stage digest by itself, whatever the
classification fix does, because the rewritten files are real protected
content, not an unclassified ambient path. `2.6.0` does not guard against it.
An update-time preflight that warns about active legacy items, and this
hazard, belong to `docs/ROADMAP.md` milestone 5. Until then, do not run
`workflow_manager update` in a repository with a `process` work item in
`IMPLEMENTING` or later unless that item's implementation review is meant
to cover the updated files.

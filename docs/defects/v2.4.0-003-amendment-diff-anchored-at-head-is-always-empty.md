# v2.4.0-003 — `AMENDMENT_DIFF.patch` is anchored at `..HEAD` and is therefore always empty at plan-review time

**Status:** **closed in `2.6.0`** (repair form 1, working-tree anchor --
see "`2.6.0` disposition" below); documented, not repaired, in `2.4.0`
through `2.5.1`. `2.4.0` is an authored release of this
repository, but its `distribution/workflow/2.4.0/` tree is frozen generated
content and its semantics are not this repository's to change outside a
Workflow release (this repository's own `CLAUDE.md`: "Never modify frozen
Workflow semantics. If migration surfaces a genuine upstream defect, write it
up under `docs/defects/` and stop there."). Repair belongs to a later
release's own checkpoint, if one adopts it.
**Found:** `implementation-review-two-stage`, `LOCAL_MODEL_PLAN_REVIEW`
round 35, finding I1 — observed on that work item's own revision-34 plan
bundle, whose `.ai-review/implementation-review-two-stage/AMENDMENT_DIFF.patch`
was written as a zero-byte file while a real, non-empty amendment diff
existed in the working tree.
**Affects:** `scripts/prepare-ai-review.sh`'s `AMENDMENT_DIFF.patch`
generation block (`workflow-2.4.0`, `D-Plan-Amendment-5`), and the identical
frozen copy at
`distribution/workflow/2.4.0/payload/scripts/prepare-ai-review.sh:471`. Every
work item with an open plan amendment, in any repository running `2.4.0` or
later, not only the one that found it.

## What it is

While a plan amendment is open (`amendment_history[-1].resolved_at_plan_revision`
still `null`), a plan-stage bundle generation writes one extra
reviewer-convenience file next to `current/`:

```sh
git diff "${base_commit}..HEAD" -- <plan-stage protected paths>
```

with `base_commit` read from the work item's own `amendment_base_commit`
(`scripts/prepare-ai-review.sh:471`). `docs/ai-workflow/REVIEW_PROTOCOL.md`'s
"Bundle structure" describes the result as the diff of "the plan-stage
protected paths since the current open amendment's own
`amendment_base_commit`", and promises the manual-external archive carries it
"so both the local and the manual-external reviewer see the identical
convenience diff".

The `..HEAD` anchor makes that promise unkeepable. At the plan stage, an
amended plan document is **uncommitted by construction**: `/request-plan-amendment`
commits `WORKFLOW_STATE.json` alone (its step 3 stages "exactly
`docs/ai-workflow/WORKFLOW_STATE.json`, never a broader `git add`"), the
amended `plan_path`/`registry_path` are then written into the working tree by
`/milestone-plan` or `/apply-plan-review`, and nothing commits them until
`/approve-review plan` runs — which is *after* both plan-review stages, i.e.
after every moment this file exists to serve. So the range
`amendment_base_commit..HEAD` spans only the state-only amendment-request
commit, which touches no plan-stage protected path, and the diff is empty.

This is not a per-work-item accident. It follows from the ordering the
mechanism itself defines, so the file is empty for **every** amendment, in
every repository, at exactly the moment it is meant to be read.

## Reproduction

Against `implementation-review-two-stage` at its revision-34 plan bundle
(`amendment_base_commit` `20a808d1ddd94e1fb2ad2efc3e4fdef6a1a64ad7`, `HEAD`
`ab3dc4130357e8dd14b915da8e232d544494e337`):

```console
$ ls -l .ai-review/implementation-review-two-stage/AMENDMENT_DIFF.patch
-rw-r--r-- 1 ... 0 ... AMENDMENT_DIFF.patch

$ git diff 20a808d1..HEAD --stat -- \
    docs/ai-workflow/IMPLEMENTATION_REVIEW_TWO_STAGE_PLAN.md \
    docs/ai-workflow/registry/implementation-review-two-stage-registry.json \
    docs/ai-workflow/requirements/implementation-review-two-stage-mapping.json
                                        # (no output — the committed range is empty)

$ git diff 20a808d1 --stat -- \
    docs/ai-workflow/IMPLEMENTATION_REVIEW_TWO_STAGE_PLAN.md \
    docs/ai-workflow/registry/implementation-review-two-stage-registry.json \
    docs/ai-workflow/requirements/implementation-review-two-stage-mapping.json
 .../IMPLEMENTATION_REVIEW_TWO_STAGE_PLAN.md       | 33 +++++++++++++++++++++-
 .../implementation-review-two-stage-registry.json |  2 +-
 2 files changed, 33 insertions(+), 2 deletions(-)
```

The worktree-anchored form (`git diff <base>` with no `..HEAD`) returns
exactly the amendment's real content. The shipped form returns nothing.

## Why it is not merely cosmetic

The file is correctly declared reviewer convenience only — it sits outside
`bundle_dir`, is hashed into neither `bundle_id` nor `review_content_id`, and
`REVIEW_REQUEST.md` carries a fixed line saying so. Nothing about identity,
approval, or reconciliation depends on it, which is why this is a
review-apparatus defect and not a correctness one.

The cost is to the reviewer, and it is a cost the mechanism creates rather
than merely fails to remove. A manual external reviewer receives
`review-bundle.tar.gz` containing an `AMENDMENT_DIFF.patch` that
`REVIEW_REQUEST.md` describes as the amendment's diff, opens it, and finds it
empty. The available readings — "the amendment changed nothing", "the diff
failed to generate", "I am looking at the wrong file" — are all wrong, and
none is distinguishable from the artifact itself. The reviewer's fallback is
to derive the amendment's extent from `DIFF.patch` (which does contain it,
mixed with every other change since `base_commit`) or from the plan document
directly, which is precisely the work the convenience file was added to save.

## Two portable repair forms

Recorded for whichever release adopts this, not implemented here.

1. **Anchor at the working tree.** Drop `..HEAD`, leaving
   `git diff <amendment_base_commit> -- <plan-stage protected paths>`. This
   matches how plan-stage identity is measured everywhere else —
   `assert_all_changed_paths_classified_worktree` and
   `compute_review_content_id_plan_stage` both read the worktree, not `HEAD` —
   so the convenience diff would finally describe the same content the
   bundle's own `review_content_id` is computed over. This is the smaller
   change and the one consistent with the rest of the plan stage.
2. **Keep `..HEAD` and generate the file at approval time instead**, when the
   amended plan is committed. This preserves a commit-anchored artifact but
   moves it past both review stages, which defeats the stated purpose
   ("so both the local and the manual-external reviewer see the identical
   convenience diff") — recorded for completeness, not recommended.

Either way, `docs/ai-workflow/REVIEW_PROTOCOL.md`'s "Bundle structure"
paragraph and `/request-plan-amendment.md` step 4's own description must be
restated to match whichever anchor is chosen, since both currently describe
the `..HEAD` form as if it produced the amendment's content.

## Interim mitigation for an author generating a bundle today

None in the tooling — the file is regenerated unconditionally on every
plan-stage generation and cannot be hand-populated without being overwritten.
The author's own `REVIEW_REQUEST.md` should state plainly that the file is
empty and why, and point the reviewer at `DIFF.patch` or at the
worktree-anchored `git diff` command above. `implementation-review-two-stage`'s
revision-35 `REVIEW_REQUEST.md` does exactly this.

## `2.6.0` disposition (`workflow-review-artifact-and-concurrency-hardening`, CP2, CP7)

**Closed, using repair form 1.** `2.6.0` anchors `AMENDMENT_DIFF.patch` at
the working tree instead of at `..HEAD` (the plan's section 5.5, the
`D-Plan-Amendment-5` revision).
`migration/overlays/2.6.0/payload/scripts/prepare-ai-review.sh` now runs
`git diff --no-renames <amendment_base_commit> -- <pathspec>` against the
working tree.
The pathspec is the union of the plan-stage protected paths declared at
`amendment_base_commit`, those declared now, and `<id>-artifacts.json`
itself. So the file holds the amendment's uncommitted content at
plan-review time, which is the content both reviewers need to see. `docs/ai-workflow/REVIEW_PROTOCOL.md`'s
"Bundle structure" paragraph and `request-plan-amendment.md` step 4 are
restated in the same overlay to describe the working-tree anchor, as
"Two portable repair forms" above requires.

Pinned by `workflow_fingerprint_generalization_test.py`'s
`TestPrepareAiReviewShAmendmentDiffWorkingTreeAnchor`, which drives the
real `prepare-ai-review.sh` end to end for an item whose amended plan is
still uncommitted, the state the `..HEAD` form could never show. The interim
mitigation above is no longer needed under `2.6.0`.

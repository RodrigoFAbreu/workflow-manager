# v2.3.1-003 — `/approve-review plan`'s transactional commit path requires `WORKFLOW_STATE.json` to already exist at `HEAD`

**Status:** documented, not repaired. Frozen v2.3.1 semantics are preserved.
`2.5.0` fixes this going forward (`implementation-review-two-stage` CP9) --
see "`2.5.0` disposition" below.
**Found:** live, during `plan-amendment-mechanism`'s own first `/approve-review plan`
invocation in this repository.
**Affects:** `scripts/workflow_state.py`'s `pin_plan_approval_state_blob`
(called from `/approve-review plan` step 6.2, `WF8c`'s journal-backed
plan-approval transaction).

## What it is

`pin_plan_approval_state_blob` stages the transaction's expected
post-approval `WORKFLOW_STATE.json` bytes directly into the Git index as a
blob object (`git update-index --add --cacheinfo <mode>,<sha>,<path>`),
deliberately never touching the working-tree copy until the approval commit
is durable. To construct that index entry it needs a file *mode* to reuse,
and it reads that mode from `state_path`'s entry **at `HEAD`**:

```python
mode_and_sha = _blob_mode_and_sha_at_commit(repo_root, "HEAD", str(state_path))
if mode_and_sha is None:
    raise PlanApprovalStateBlobUnavailableError(
        f"{state_path} does not exist at HEAD -- cannot determine its file mode "
        f"to pin a new blob in its place"
    )
```

If `docs/ai-workflow/WORKFLOW_STATE.json` has never been committed — i.e.
this is the very first plan approval this repository's Git history will
ever record — there is no HEAD entry to read a mode from, and the function
refuses unconditionally. There is no fallback to a default mode (`100644`,
which every other tracked file here already uses) and no path that lets the
transaction proceed by any other means.

This is not the intent-to-add-vs-fully-staged mechanics `stage_plan_approval_commit_paths`'
own precondition already documents (`DirtyIndexBeforeStagingError`) — that
class of issue is about *this invocation's own preceding index state* and is
resolvable by unstaging. This one is unconditional: no session, on any
retry, can supply a HEAD blob for a path that has genuinely never been
committed.

## Why it happened here

`workflow-manager`'s own self-hosted Workflow installation (this repository)
was bootstrapped by `workflow-manager`'s own install tooling, which writes
`docs/ai-workflow/WORKFLOW_STATE.json` to disk but does not commit it — the
file sat as an untracked (`??`) working-tree file from bootstrap through
thirty-three rounds of plan review, since no Workflow command commits it
before the first plan approval.

The original frozen Workflow's own first-ever plan approval (`workflow-v2-1-core`,
in `repflow-android`) never exercises this path either: `/approve-review`
step 4a's own "Interim scope guard" diverts that specific work item's
plan-stage approval to `/bootstrap-workflow-v2`'s own separate checklist
instead of this transactional mechanism, for as long as
`docs/ai-workflow/WORKFLOW_V2_PLAN.md` still contains the heading
`Bootstrap plan-approval procedure` — direct evidence that the original
authors already knew a repository's first-ever plan approval needs handling
distinct from the ordinary journal-based transaction. That special handling
was never generalized past `workflow-v2-1-core`'s own literal id, so a
different repository's own first-ever plan approval — this one — has no
equivalent escape hatch and hits the raw precondition instead.

## Why it is not repaired here

Repairing it means editing `scripts/workflow_state.py`'s frozen v2.3.1
behavior (defaulting to mode `100644` when no HEAD entry exists, or adding a
bootstrap branch analogous to `workflow-v2-1-core`'s own), which this
repository's own hard rule (`CLAUDE.md`) prohibits doing in place.

## How it is handled

Not yet — this defect blocked `plan-amendment-mechanism`'s own first
`/approve-review plan` attempt outright. The attempt was rolled back cleanly
via the transaction's own sanctioned rollback path (`classify_plan_approval_outcome`
returned `NOT_COMMITTED`; `rollback_plan_approval_transaction` verified the
reset) before this was written up — no commit was created, no state was
lost, the working tree is unchanged.

Resolving it is an operator decision, not something to apply unilaterally:
options include (a) a distinct, explicitly-authorized one-time commit of
`docs/ai-workflow/WORKFLOW_STATE.json`'s current, unmodified bytes, made
outside any Workflow command, to establish a HEAD entry before retrying the
ordinary transaction; or (b) a future Workflow release generalizing the
`workflow-v2-1-core`-only bootstrap escape hatch to any repository's
genuinely-first plan approval.

## If a future release repairs it

The portable form is either: default `pin_plan_approval_state_blob`'s mode
to `100644` (matching every other tracked path this Workflow ever commits)
when `_blob_mode_and_sha_at_commit` returns `None` rather than refusing
unconditionally; or generalize `/approve-review`'s `workflow-v2-1-core`-only
bootstrap diversion in step 4a to any work item whose repository has never
committed `WORKFLOW_STATE.json`. Either is a change to Workflow source and
belongs in a Workflow release, not in this repository.

## `2.5.0` disposition (`implementation-review-two-stage`, §8, CP13)

**Fixed (CP9).** This record's own first portable form (above) was adopted
verbatim in `migration/overlays/2.5.0/payload/scripts/workflow_state.py`:
`pin_plan_approval_state_blob` now falls back to file mode `100644`
(`_FALLBACK_STATE_BLOB_MODE`) when `_blob_mode_and_sha_at_commit` finds no
`HEAD` entry for `state_path`, instead of raising
`PlanApprovalStateBlobUnavailableError` unconditionally. The exception
class is retained (documented, no longer raised by this function) rather
than deleted, since nothing else in this module's public contract depends
on its removal. The overlay's own `scripts/workflow_integration_test.py`
proves it, in
`TestPlanApprovalStateBlobPinAndMaterialize.test_pin_defaults_to_mode_100644_when_state_path_absent_at_head`:
the pin succeeds, stages mode `100644`, and the staged content matches
exactly.

This repository's own first-ever plan approval already recovered by a
different route (`plan-amendment-mechanism` committed
`WORKFLOW_STATE.json` before this milestone began, per option (a) above)
and is unaffected either way; the fix is for every *other* repository's
own genuinely-first plan approval, which no longer hits this refusal after
updating to `2.5.0`.

# Release history

> For: someone choosing a Manager version or wondering what changed. Last checked with: Workflow Manager 1.20.0, Workflow 2.29.1.

One line per Workflow Manager release, newest first. The Manager's version is the Git tag. Each release links to its GitHub page, which lists the changes and carries the files. A Manager release carries no Workflow release of its own. The last column says which Workflow releases it can install.

| Manager | Date | What changed, in plain words | Workflow releases it installs | Release page |
|---|---|---|---|---|
| 1.20.0 | 2026-11-14 | New option `doctor --retention --json`: the retention alert as one JSON document for another program to read, instead of the text. It is read-only, never changes an exit code, and prints only the document (exit 0 whenever it is printed). The document has the policy state, whether the evaluation ran and why not, whether the report is complete, one entry per threshold with its current value, whether it is reached and a stable key, and a snapshot of the counts and the finished items that were archived and removed. It is documented in `docs/retention.md`. The text output of `verify` and `doctor` is unchanged. |
| 1.19.1 | 2026-11-14 | Fix for the retention alert's age threshold. When only the age threshold is reached, the alert's `next:` step now names a finished item that `retention-cleanup` would really plan (an old one, beyond the 3 most recent), not a young one; the alert and the cleanup choose it with the same function. The alert example in `docs/retention.md` is now a complete report. Nothing changes for the count and size thresholds. |
| 1.19.0 | 2026-11-14 | New optional retention policy key `thresholds.finished_max_age_days` (1 to 3650): finished work items older than that many days, beyond the 3 most recent, count toward the retention alert and are planned by `retention-cleanup` (modes `cleanup` and `both`), oldest first, within the existing limit of 5 per run. An item whose completion time cannot be read is never counted as old, and the alert and the preview say how many were not known. Nothing changes when the key is absent. A policy file that carries the new key is refused by older Managers, which then fall back to `off`. |
| 1.18.1 | 2026-11-13 | Wording fix for the retention commands. `retention-cleanup` now says exactly when it exits 1 (the run stopped after its first per-item call was attempted, even if its script could not be started) and when it exits 2 (refused, or stopped before that first call). A stop report after an item that already had an archive says this run did not create one, and a failed undo says the item may or may not be archived. The preview's `next:` line now shows the real target, quoted for a shell, instead of `TARGET`. No behaviour changes. |
| 1.18.0 | 2026-11-12 | `retention-cleanup TARGET --confirm SENTENCE` now runs the cleanup that 1.17.0 only previewed: for the finished items the preview listed, it archives each one, checks the archive, then removes it, and stops at the first failure. It runs only when you adopted a retention policy in `cleanup` or `both` mode, both policy files are committed, and you pass the exact sentence bound to the plan the preview printed. It never prunes archives and commits nothing. Without an adopted `cleanup` or `both` policy nothing changes. | 2.3.1 and every later published release | [v1.18.0](https://github.com/RodrigoFAbreu/workflow-manager/releases/tag/v1.18.0) |
| 1.17.0 | 2026-11-11 | New command `retention-cleanup TARGET`: a read-only preview of what an adopted retention policy in `cleanup` or `both` mode would archive and remove. It checks that the policy is adopted and unchanged, both policy files are committed, no tracked file is changed, the installed Workflow release is 2.25.5 or later and no removal was interrupted, then lists the oldest finished items (at most 5 per run) with a plan digest. It writes nothing and never runs prune. Also: the retention alert's wording is exact when a report is incomplete, and a Manager command name is no longer taken for an internal id by the docs check. | 2.3.1 and every later published release | [v1.17.0](https://github.com/RodrigoFAbreu/workflow-manager/releases/tag/v1.17.0) |
| 1.16.0 | 2026-11-09 | `verify` and `doctor` now print a `retention alert:` block when an adopted retention policy in mode notify or both has a threshold reached (finished items, finished folders in MiB, archives or prunable archives), or one `not evaluated` line saying why it could not be checked. Nothing else changes for a repository without an adopted notify or both policy, and no exit code changes. `adopt-retention-policy` also refuses impossible dates, names its link and non-regular-file refusals in its help, and syncs the record's directory. | 2.3.1 and every later published release | [v1.16.0](https://github.com/RodrigoFAbreu/workflow-manager/releases/tag/v1.16.0) |
| 1.15.0 | 2026-11-09 | New command `adopt-retention-policy TARGET`: it previews and, with a confirmation sentence, adopts a retention policy file (mode off, notify, cleanup or both, and thresholds). `status --retention` and `doctor --retention` show the policy's state. Nothing alerts or cleans yet, and with no policy file nothing changes. | 2.3.1 and every later published release | [v1.15.0](https://github.com/RodrigoFAbreu/workflow-manager/releases/tag/v1.15.0) |
| 1.14.8 | 2026-11-04 | The retention view counts what it echoes by one rule, states its limits in words, and tests every cause exactly; nothing else changes for someone installing. | 2.3.1 and every later published release | [v1.14.8](https://github.com/RodrigoFAbreu/workflow-manager/releases/tag/v1.14.8) |

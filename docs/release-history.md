# Release history

> For: someone choosing a Manager version or wondering what changed. Last checked with: Workflow Manager 1.23.1, Workflow 2.29.1.

One line per Workflow Manager release, newest first. The Manager's version is the Git tag. Each release links to its GitHub page, which lists the changes and carries the files. A Manager release carries no Workflow release of its own. The last column says which Workflow releases it can install.

| Manager | Date | What changed, in plain words | Workflow releases it installs | Release page |
|---|---|---|---|---|
| 1.23.1 | 2026-11-23 | Fix in the wording of `adopt-retention-policy`. For a policy file that carries the `unattended` key but was adopted only with the ordinary sentence, the adopt preview no longer tells the operator to run the command they are already running: it says to adopt again with the unattended sentence printed below it. `status`, `doctor` and the cleanup preview keep their text. The refusal of a confirmation that mixes the two sentences is pinned in full, and the retention page says that the owner adopts the policy again after an update turns a record invalid. No behaviour changes. |
| 1.23.0 | 2026-11-19 | `retention-cleanup --unattended` also prunes archives, when the adopted unattended policy has `unattended.prune` true. After the archive-and-remove phase it deletes the archives of finished items whose review folder is already gone and that are strictly older than the policy's `ttl_days`, oldest first, at most `prune_max_per_run` per run, one archive per engine call; it never selects an archive whose review folder is present or an id under an interrupted removal, and it requires the engine's dry run to list exactly the planned set before applying. The policy is re-read before every call, the first failure stops the run, every prune action and refusal is written to the audit file, and `--json` carries the prune results. A deleted archive cannot be undone, and the archive store is not backed up. `status`, `doctor` and the previews say what an unattended adoption would delete. |
| 1.22.0 | 2026-11-19 | New option `retention-cleanup --unattended`: the archive-and-remove cleanup of a repository whose policy the owner adopted with the unattended sentence (1.21.0) runs without the per-plan confirmation. It refuses unless the adoption authorises it (`cleanup` true, mode `cleanup` or `both`, adopted with the unattended sentence), keeps every earlier safeguard (committed and unchanged policy, clean tree, a complete report, no interrupted removal, the per-run cap, the policy re-read before each item, the first failure stops the run), skips the newest `keep_recent` finished items, and writes one line per action or refusal to an append-only audit file outside the repository (`$XDG_STATE_HOME/workflow-manager/retention-audit.jsonl`, mode 0600); it refuses before any action when that file cannot be written. `--json` prints the run as one document. The preview and the confirmed run show the same plan. Pruning archives is not run unattended yet. |
| 1.21.0 | 2026-11-18 | New closed policy key `unattended` for the retention policy, with its own adoption sentence. `unattended` declares what an unattended run may do (`cleanup`, `prune`, `keep_recent` of at least 3, `ttl_days` from 14 to 3650, `prune_max_per_run`) and is adopted only with `Adopt the unattended retention policy`, then the first 12 characters of the digest and a full stop; the ordinary sentence never authorises it. `adopt-retention-policy`, `status`, `doctor` and the cleanup preview print what an unattended adoption would authorise. Nothing runs unattended yet: `retention-cleanup` still needs its per-plan confirmation, and an older Manager reads a file carrying the key as mode `off`. |
| 1.20.3 | 2026-11-16 | Fix in the retention report. A report with read errors, nothing finished or kept and only failed forge queries now shows as incomplete with its read errors, as `docs/retention.md` says, instead of printing the forge note; the alert and the JSON alert follow for that report only. A complete report is unchanged. The doctor commands share one refusal block, and the retention page's limits, the age step's exception and the link texts to the page are exact and pinned by tests. |
| 1.20.2 | 2026-11-16 | Fix in the report of `update --dry-run` for a null or damaged installation record. When the installed release cannot be read, the "not verified" note no longer prints a `verify` command that a bare `verify` refuses; it says the record names no usable release. The report of a valid record is unchanged (byte-identical). The check for "is this a release version" now has a single definition shared by the report and the dry run. |
| 1.20.1 | 2026-11-15 | Fixes in how `update` treats damaged and null installation records and null-manifest releases. `update --dry-run` now predicts what the real `update` does: it accepts a damaged record when you name a release (a recorded name such as `../escaped` never reaches a cache path), and it says when the installation record would be rewritten instead of printing `(no change)`. A release directory whose manifest has no version is now refused, with a cause and one step, by `bootstrap`, `update`, `verify`, `status` and `doctor`; they accepted it before, and `update` wrote the record as `workflow None`. The recovery steps keep an explicit `--release-version` when it names the latest release. Output of working installations is unchanged. |
| 1.20.0 | 2026-11-14 | New option `doctor --retention --json`: the retention alert as one JSON document for another program to read, instead of the text. It is read-only, never changes an exit code, and prints only the document (exit 0 whenever it is printed). The document has the policy state, whether the evaluation ran and why not, whether the report is complete, one entry per threshold with its current value, whether it is reached and a stable key, and a snapshot of the counts and the finished items that were archived and removed. It is documented in `docs/retention.md`. The text output of `verify` and `doctor` is unchanged. |
| 1.19.1 | 2026-11-14 | Fix for the retention alert's age threshold. When only the age threshold is reached, the alert's `next:` step now names a finished item that `retention-cleanup` would really plan (an old one, beyond the 3 most recent), not a young one; the alert and the cleanup choose it with the same function. The alert example in `docs/retention.md` is now a complete report. Nothing changes for the count and size thresholds. |
| 1.19.0 | 2026-11-14 | New optional retention policy key `thresholds.finished_max_age_days` (1 to 3650): finished work items older than that many days, beyond the 3 most recent, count toward the retention alert and are planned by `retention-cleanup` (modes `cleanup` and `both`), oldest first, within the existing limit of 5 per run. An item whose completion time cannot be read is never counted as old, and the alert and the preview say how many were not known. Nothing changes when the key is absent. A policy file that carries the new key is refused by older Managers, which then fall back to `off`. |
| 1.18.1 | 2026-11-13 | Wording fix for the retention commands. `retention-cleanup` now says exactly when it exits 1 (the run stopped after its first per-item call was attempted, even if its script could not be started) and when it exits 2 (refused, or stopped before that first call). A stop report after an item that already had an archive says this run did not create one, and a failed undo says the item may or may not be archived. The preview's `next:` line now shows the real target, quoted for a shell, instead of `TARGET`. No behaviour changes. |
| 1.18.0 | 2026-11-12 | `retention-cleanup TARGET --confirm SENTENCE` now runs the cleanup that 1.17.0 only previewed: for the finished items the preview listed, it archives each one, checks the archive, then removes it, and stops at the first failure. It runs only when you adopted a retention policy in `cleanup` or `both` mode, both policy files are committed, and you pass the exact sentence bound to the plan the preview printed. It never prunes archives and commits nothing. Without an adopted `cleanup` or `both` policy nothing changes. | 2.3.1 and every later published release | [v1.18.0](https://github.com/RodrigoFAbreu/workflow-manager/releases/tag/v1.18.0) |
| 1.17.0 | 2026-11-11 | New command `retention-cleanup TARGET`: a read-only preview of what an adopted retention policy in `cleanup` or `both` mode would archive and remove. It checks that the policy is adopted and unchanged, both policy files are committed, no tracked file is changed, the installed Workflow release is 2.25.5 or later and no removal was interrupted, then lists the oldest finished items (at most 5 per run) with a plan digest. It writes nothing and never runs prune. Also: the retention alert's wording is exact when a report is incomplete, and a Manager command name is no longer taken for an internal id by the docs check. | 2.3.1 and every later published release | [v1.17.0](https://github.com/RodrigoFAbreu/workflow-manager/releases/tag/v1.17.0) |
| 1.16.0 | 2026-11-09 | `verify` and `doctor` now print a `retention alert:` block when an adopted retention policy in mode notify or both has a threshold reached (finished items, finished folders in MiB, archives or prunable archives), or one `not evaluated` line saying why it could not be checked. Nothing else changes for a repository without an adopted notify or both policy, and no exit code changes. `adopt-retention-policy` also refuses impossible dates, names its link and non-regular-file refusals in its help, and syncs the record's directory. | 2.3.1 and every later published release | [v1.16.0](https://github.com/RodrigoFAbreu/workflow-manager/releases/tag/v1.16.0) |

Nothing alerts or cleans yet, and with no policy file nothing changes. | 2.3.1 and every later published release | [v1.15.0](https://github.com/RodrigoFAbreu/workflow-manager/releases/tag/v1.15.0) |

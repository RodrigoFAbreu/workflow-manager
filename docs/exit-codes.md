# Exit codes

> For: anyone who runs `workflow-manager` from a script or wants to know what a status means. Last checked with: Workflow Manager 1.8.0, Workflow 2.12.0.

Every command ends with a status. This is the one table of them. Every error message names its cause (`error:`) and one step to take (`next:`); the exit code is the contract, and the message text can improve between releases. The fix for each message, in more words, is in [common problems](common-problems.md).

| Code | Command | Meaning | What to do |
|---|---|---|---|
| 0 | every command | It succeeded. `verify` found no problems. `status` found the repository intact, or not managed (it also prints the work in flight). `doctor` found nothing to warn about. `update --dry-run` printed its report and the real update would not be refused. `package verify` accepted the archive. | Nothing. |
| 1 | `verify`, `status` | The installed files differ from the release (`N problem(s)`). | Run `update` to put the release's files back (add `--force` if a line says `modified:` for a release file, which replaces your edit), or undo the listed edits with `git checkout -- <file>`. |
| any | `status --retention`, `doctor --retention` | Nothing: the retention section is informational, so the option never changes an exit code. When the report is unavailable or incomplete the section says so and the command exits as it would without the option. | Read the section's `next:` line; see [Retention report](retention.md). |
| 1 | `status` of a managed repository | It could not prove that its writes stay outside the repository: Git cannot run, or the release cache, its lock or a temporary directory lies inside the repository or `.git`. (A repository that is not managed still exits 0.) | Choose another cache with `--release-cache`, unset `TMPDIR`, or make Git available. |
| 1 | any command that reads or writes the repository (`bootstrap`, `update`, `verify`, `status`, `doctor`, `uninstall`) | A file error that is not a refusal: a permission error, a full disk. The message prints the system's text and a `next:` step. | Fix the cause, then follow the `next:` line. It says whether to run the command again; do not, while Workflow data is missing and the line says so. |
| 1 | `update`, `update --dry-run` | No usable release at or above the installed one: with no `--release-version`, the newest release that can be had (offline, its archive cannot be fetched, the source was read and holds none at or above it, or `--pinned-only` offers only pins older than the installed release) is older than the one the repository records, and a bare `update` never goes back. Nothing is installed or written. | Connect to the network, point `--release-source` at a mirror that holds the release, or name an older release with `--release-version` if you mean to go back. With `--pinned-only` (or `WORKFLOW_MANAGER_PINNED_ONLY`), run the command again without it. |
| 1 | `bootstrap`, `update`, `update --dry-run` | The release you named with `--release-version` (or `--release-dir`) needs a newer Manager than this one: its manifest says so, and the message names the Manager to install. A bare `bootstrap` or `update` skips such a release with one note and installs the newest one this Manager can; if nothing at or above the installed release is left, a bare `update` stops with the refusal in the row above. `doctor` reports the same case as exit 2, and `status` and `verify` only print a note. | Upgrade the Manager to the version the message names, then run the same command again. |
| 1 | `doctor` | At least one finding is `blocked` or a `warning`. An incomplete inspection counts as a warning. | Read the report and its recovery lines before you update. |
| 1 | any command that needs a Workflow release (`bootstrap`, `update`, `update --dry-run`, `verify`, `status`) | No usable release: the version is not pinned, it is not cached and cannot be downloaded, or a download fails its digest, size or manifest check. | Connect to the network once, point `--release-source` at a mirror, or install a newer Manager. If a digest does not match after a retry, do not install, and report it. |
| 1 | `bootstrap`, `update`, `update --dry-run`, `verify`, `status` | A release name that is not `X.Y.Z` (`v2.12.0`, `2.12`, a path), or an installation record whose `workflow_version` is not one (`null` included). `status` and `verify` accept a valid explicit `--release-version`. `status` of a typed name prints only the refusal. | Name the release `X.Y.Z`, as `workflow-manager releases` lists it; for a damaged record, see [common problems](common-problems.md). |
| 2 | every command | The command line did not parse: an unknown command or option, or a missing argument. | Put global options such as `--release-version` before the command: `workflow-manager --release-version 2.9.0 update <repo>`. |
| 2 | `bootstrap` | The target does not exist or is not a Git repository, it is already managed (or its record is unreadable), or it has files in the way of the release's files. A directory (or a file where a directory goes) in the way is refused too, with or without `--force`. | Use `update` for a managed repository, run `git init`, or move your files away or re-run with `--force`. For an unreadable record, delete `.workflow-manager/` and bootstrap again. |
| 2 | `update`, `update --dry-run` | The repository is not managed, its record is unreadable, managed files were edited locally, or the release needs paths the repository uses for something else. The dry run refuses in the same cases as the real update. The dry run also refuses when the release cache or a temporary directory named in the environment is inside the repository. | Run `bootstrap` first; save your edits and re-run with `--force`; or move the files in the way. For an unreadable record, delete `.workflow-manager/` and bootstrap again. For the cache or temporary directory, choose another cache with `--release-cache`, or unset `TMPDIR`. |
| 2 | `doctor` | It could not check: the repository is not managed, its record is unreadable, or the target release could not be resolved (including that no usable release reaches the installed one: the refusal of the `update` row above, with its `next:` line, and nothing on stdout), or a `--release-dir` manifest is malformed (a release it cannot read exits 2, not a traceback's 1). It also refuses when the release cache or a temporary directory named in the environment is inside the repository. | Fix what the message names, then run it again. Choose another cache with `--release-cache`, or unset `TMPDIR`. |
| 2 | `doctor` | A release name that is not `X.Y.Z`, or an installation record whose `workflow_version` is not one (`null` included). | Name the release `X.Y.Z`, or repair the record; see [common problems](common-problems.md). |
| 2 | `verify` | The repository is not managed, or its record is unreadable. | Run `bootstrap`, or delete `.workflow-manager/` and bootstrap again. |
| 2 | `status` | Its record is unreadable. (A repository that is not managed is exit 0.) | Delete `.workflow-manager/` and run `bootstrap` again. |
| 2 | `uninstall` | The repository is not managed, or its record is unreadable. | Delete `.workflow-manager/` by hand if the record is damaged. |
| 1 | `package verify` | The archive does not match `--sha256`, cannot be read, or is not a valid package. | Download the archive again and check it against `SHA256SUMS`. |

## Global options

The options `--release-version`, `--release-source`, `--release-cache`, `--release-dir` and `--pinned-only` go before the command, not after it: `workflow-manager --release-version 2.9.0 update <repo>`. Written after the command they do not parse, and the command exits 2.

`--pinned-only` (or `WORKFLOW_MANAGER_PINNED_ONLY=1`) installs only the releases this Manager pins and never looks for newer ones; without it a bare `bootstrap` or `update` means the newest release the source publishes, verified by its own `SHA256SUMS`. `releases` exits 0. `package build` exits 0 when it finishes, and 1 when the directory is not a valid release.

Some causes that used to end as a Python traceback with exit 1 are now refusals with exit 2 and a `next:` step: a directory at the installation record (`.workflow-manager/installation.json`), a directory or a file in the way of a release path, and a `--release-dir` manifest that crashes `doctor`. A `status` of a managed repository that cannot prove its writes stay outside the repository now exits 1, where it exited 0. A file error such as a permission error exits 1 with the system's message and a `next:` step.

Use them in scripts: `workflow-manager verify <repo> && echo ok`.

## Maintainer tools

`tools/release_lock.py` maintains the tested-releases lock ([Releasing](RELEASING.md#a-new-workflow-release)); it is a checkout tool, not part of the `workflow-manager` command.

| Code | Command | Meaning | What to do |
|---|---|---|---|
| 0 | `add`, `check`, `latest` | It succeeded: the entry was written, the lock matches what the source publishes, or the lock with the newest release was written to `--out`. | Nothing. |
| 1 | `add`, `check`, `latest` | A verification failure (an asset does not match its `SHA256SUMS`, a digest differs from what the source publishes) or a refused lock. `add` of a pinned version is refused: every pin is already tested in every run, so no lock change is needed. | Follow the message. For a pinned version, do nothing; `add` is for a release published after the last pin. |
| 2 | every command | The command line did not parse. | Run `python3 tools/release_lock.py --help`. |

`tools/lock_digest.py LOCK COMMITTED` prints the nightly's release-cache key suffix ([Architecture](ARCHITECTURE.md#verification-execution)): nothing when the two locks hold the same JSON, otherwise `-` and 16 hex digits of the lock's digest. It exits 0 when it printed the suffix and 2 when the command line did not name two files or a lock could not be read or parsed; the workflow step then fails rather than fall back to a key without the suffix.
